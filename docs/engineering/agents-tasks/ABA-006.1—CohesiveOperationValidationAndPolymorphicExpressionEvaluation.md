Objective

Refine the ABA-006 validation implementation so validation behavior is owned cohesively by the domain objects that represent it.

Replace the centralized recursive Evaluate type switch with polymorphic evaluation on the sealed expression types, and make Operation the primary validation entry point.

The resulting domain flow should read naturally:

Operation.Validate(operands)
        ↓
ValidationDefinition.Expression.evaluate(operands)
        ↓
ComparisonExpression / AllOfExpression

This is a focused architectural refinement. It must not expand the validation vocabulary or introduce REST behavior.

Design intent

The operation should own its full domain behavior:

type Operation struct {
    Definition OperationDefinition
    Execute    ExecuteFunc
}

func (operation Operation) Validate(
    operands []float64,
) (*ValidationDefinition, error)

Adding a new operation should remain localized in its operation declaration:

metadata
operands
validations
executor

There must be no operation-ID-based validation dispatcher elsewhere.

Expression nodes should own the semantics of their own expression type.

Required changes
1. Expression evaluation contract

Extend the sealed Expression contract with an unexported evaluation method:

type Expression interface {
    expressionNode()
    evaluate(operands []float64) (bool, error)
}

The method must remain unexported so external packages cannot add unsupported expression types.

Do not expose a general-purpose evaluator interface publicly.

2. ComparisonExpression behavior

Implement evaluation directly on ComparisonExpression.

It must:

resolve the referenced operand explicitly;
return an error for an unsupported operand reference;
return an error when the referenced operand is absent;
apply its comparison operator;
return an error for an unsupported comparison operator.

A missing second operand must not silently behave as numeric zero.

Use a small helper when useful:

func resolveOperand(
    reference OperandReference,
    operands []float64,
) (float64, error)

Errors must include enough context to identify the invalid reference or missing position.

3. AllOfExpression behavior

Implement evaluation directly on AllOfExpression.

Required behavior:

evaluate children in declaration order;
short-circuit on the first failed child;
propagate evaluation errors with context;
preserve vacuous truth for an empty expression slice unless registry validation later forbids it.

Do not add anyOf, not, or other operators.

4. Operation validation

Add:

func (operation Operation) Validate(
    operands []float64,
) (*ValidationDefinition, error)

Behavior:

iterate validations in declaration order;
evaluate each expression;
return the first violated validation;
return nil, nil when all validations pass;
return a contextual error when a validation definition cannot be evaluated.

The error should identify:

operation ID;
validation ID;
underlying expression error.

Do not allocate violation collections.

5. Remove or reduce centralized evaluation

Remove the exported centralized:

Evaluate(expression, operands)

unless a real consumer still requires it.

Tests should exercise expression behavior through:

package-level access where appropriate;
Operation.Validate as the primary public domain path.

Do not retain two competing validation entry points.

6. Validate Operation, not OperationDefinition

Replace:

Validate(definition OperationDefinition, operands []float64)

with the method on Operation.

The domain caller should use:

violation, err := operation.Validate(operands)

This keeps execution and validation capabilities together on the registered operation.

7. Preserve function-based execution

Do not introduce concrete operation strategy types such as:

AdditionStrategy
DivisionStrategy
SquareRootStrategy

Continue using:

Execute ExecuteFunc

The desired design combines:

function-based arithmetic execution;
operation-owned validation;
expression-owned evaluation.
8. Registry definition validation

Extend registry construction validation only as needed to reject malformed validation definitions before startup completes.

At minimum consider validating:

validation ID is non-empty;
validation message is non-empty;
expression is non-nil;
operand references are compatible with operation arity;
comparison operators are supported;
AllOfExpression children are recursively valid and non-nil.

Prefer fail-fast startup validation over discovering malformed backend-authored expressions during a user request.

Keep validation logic proportional and recursive only over the two supported expression types.

9. Deep-copy expression trees

Reassess the immutability claim.

AllOfExpression contains:

Expressions []Expression

Copying only the top-level []ValidationDefinition does not necessarily prevent aliasing of nested child slices.

Implement a small recursive copy mechanism for the closed expression hierarchy, for example:

func copyExpression(expression Expression) Expression

It should:

copy ComparisonExpression by value;
recursively copy AllOfExpression.Expressions;
preserve registry immutability even if the caller mutates its source expression tree after NewRegistry.

Do not use reflection or generic cloning.

10. Preserve JSON contract

The serialized manifest must remain exactly compatible with the current TypeScript discriminated union:

{
  "kind": "comparison",
  "operand": "second",
  "operator": "notEqual",
  "value": 0
}

and:

{
  "kind": "allOf",
  "expressions": []
}

The refactoring must not alter the wire contract.
