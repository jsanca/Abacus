Scope
1. Reproduce the continuation behavior

Reproduce this exact flow against the real Docker stack:

144 ÷ 12 = 12

Then select Multiplication.

Expected state:

selected operation = multiplication
Operand 1 = "12"
Operand 2 = ""
focus = Operand 2
previous expression/result transition appropriately

Confirm focus programmatically using:

document.activeElement

Do not rely only on visual focus appearance.

Also reproduce continuation from a unary result:

√144 = 12

Then select Addition.

Expected:

Operand 1 = "12"
Operand 2 = ""
focus = Operand 2
2. Correct focus management if required

If the current behavior does not focus the expected input, fix the smallest responsible frontend boundary.

Requirements:

selecting a binary operator after a resolved result focuses Operand 2;
selecting a unary operator after a resolved result focuses Operand 1;
state updates must complete before focus is applied;
no setTimeout(..., 0) timing workaround;
no stale refs or stale callbacks;
no focus stealing during ordinary input editing;
no generalized focus framework.

Prefer the existing explicit focus-intent/effect model established during ABA-004 remediation.

3. Clear continuation state correctly

When selecting a new operation after a successful result:

move the previous numeric result into Operand 1;
clear Operand 2;
clear or transition the previous completed expression as agreed;
clear stale validation and service errors;
set the calculator state to editing;
focus the correct operand.

Do not clear operand values immediately when a calculation succeeds. The completed calculation must remain visible until the user begins another operation.

4. Percentage expression formatting

Current backend output:

{
  "expression": "200 % 15",
  "result": 30
}

Required output:

{
  "expression": "15% of 200",
  "result": 30
}

The calculation request remains:

{
  "operationId": "percentage",
  "operands": [200, 15]
}

where:

operands[0] = base
operands[1] = percentage

Do not change percentage calculation semantics.

5. Keep expression formatting cohesive

Do not add an operation-ID switch inside the HTTP handler.

The handler should not contain:

switch operation.Definition.ID

or:

if operationID == "percentage"

Prefer a function-based formatting strategy owned by the operation, analogous to ExecuteFunc, when it provides the clearest proportional solution.

A possible direction:

type FormatExpressionFunc func(
    definition OperationDefinition,
    operands []float64,
) (string, error)

and:

type Operation struct {
    Definition       OperationDefinition
    Validate         ...
    Execute          ExecuteFunc
    FormatExpression FormatExpressionFunc
}

The exact shape is not prescribed. A simpler solution is welcome if it:

keeps operation-specific formatting with the operation;
avoids transport-level dispatch;
supports unary, ordinary binary and percentage notation;
remains proportional.

Do not create concrete formatter classes or a generic template language.

6. Formatting behavior

Preserve:

10 + 5
5 − 10
2.5 × 4
144 ÷ 12
2 xʸ 8
√144

Change only percentage to:

15% of 200

Wrong arity must not panic during formatting.

Return a contextual internal error when expression formatting cannot proceed.
