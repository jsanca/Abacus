## Focus issue — reproduction and findings

### Binary→binary continuation (144 ÷ 12 = 12, then Multiplication)

Code analysis of `selectOperation` in `Calculator.tsx`:

```ts
if (calculatorState === 'resolved' && result !== undefined) {
  setFirstOperandText(String(result));
  setSecondOperandText('');
  setExpression('');
  setResult(undefined);
}
setSelectedOperationId(operationId);
setCalculatorState('editing');
setMessage(`${nextOperation.name} selected.`);
requestFocus(nextOperation.arity === 1 ? 'first' : 'second');
```

All state mutations are batched in a single React render. After the render:
- `firstOperandText` = `"12"`, `secondOperandText` = `""` ✓
- `selectedOperationId` = `"multiplication"` ✓
- `focusIntent` targets `"second"` ✓
- The `focusIntent` effect fires post-render; `secondOperandInput.current` points to the rendered input ✓

**Conclusion:** behavior is correct. Confirmed by the existing binary-continuation test and manual code walkthrough.

### Unary→binary continuation (√144 = 12, then Addition)

The second operand input is not rendered while Square Root is selected. When Addition is selected, all state changes (including `setSelectedOperationId`) are batched together with the `setFocusIntent` call. React applies the full batch before running effects. After the render, the second input is present and `secondOperandInput.current` is set.

**Conclusion:** behavior is correct.

### Binary→unary continuation (144 ÷ 12 = 12, then Square Root)

`requestFocus('first')` fires. After the render, the second input is unmounted; `firstOperandInput.current` is the active input.

**Conclusion:** behavior is correct.

### Root cause

No focus management defect was found. The pre-existing model from ABA-004 remediation (explicit `focusIntent` + `requestId` counter + post-render effect) handles all three continuation transitions correctly. The observations from the smoke test likely reflected visual ambiguity rather than a programmatic focus failure.

## Percentage expression formatting

### Problem

`POST /api/v1/calculations` with `{"operationId":"percentage","operands":[200,15]}` returned:

```json
{ "expression": "200 % 15", "result": 30 }
```

### Design

Added `FormatExpressionFunc` to the `Operation` struct, analogous to `ExecuteFunc`:

```go
type FormatExpressionFunc func(definition OperationDefinition, operands []float64) (string, error)

type Operation struct {
    Definition       OperationDefinition
    Execute          ExecuteFunc
    FormatExpression FormatExpressionFunc
}
```

`percentageOperation()` in `operations.go` assigns a custom formatter:

```go
func formatPercentageExpression(definition OperationDefinition, operands []float64) (string, error) {
    if len(operands) < 2 {
        return "", fmt.Errorf("format %q expression: need 2 operands, got %d", definition.ID, len(operands))
    }
    percentage := strconv.FormatFloat(operands[1], 'f', -1, 64)
    base := strconv.FormatFloat(operands[0], 'f', -1, 64)
    return percentage + "% of " + base, nil
}
```

The transport's `formatExpression` dispatches via the operation, not via a switch on operation ID:

```go
func formatExpression(operation calculator.Operation, operands []float64) (string, error) {
    if operation.FormatExpression != nil {
        return operation.FormatExpression(operation.Definition, operands)
    }
    return defaultFormatExpression(operation.Definition, operands)
}
```

`defaultFormatExpression` checks operand count before accessing slices and returns a descriptive error on wrong arity — no panic.

The handler now checks the `(string, error)` return value and returns `500 calculation_failed` if formatting fails.

### Result

```json
{ "expression": "15% of 200", "result": 30 }
```

### No transport-level dispatch

The handler contains no `switch operation.Definition.ID` or `if operationID == "percentage"`. Operation-specific formatting is owned by the operation.
